# PulseLib: 26.1.2 MultiLoader → 26.2 MultiLoader

## Правила продолжения

При каждом запуске сначала прочитать этот журнал и `AGENTS.md`, затем выполнить `git status --short --branch` и проверить HEAD/исходные refs. Выполнять только следующий незавершённый этап; после него обновить журнал, создать локальный коммит, предоставить отчёт и остановиться. Текущее состояние — в таблице этапов и последней записи журнала.

Канонический источник — современная MultiLoader-архитектура. `master` используется только как донор адаптации к Minecraft 26.2. Не делать merge веток, не подменять современные очереди, графы, plugin lifecycle или player rendering старыми реализациями. Не публиковать артефакты, не делать push/force push, не трогать пользовательские миры. Сборка или наличие `RenderSystem.getDevice()` не подтверждают работу GPU backend.

### Область baseline API

Baseline построен через `JavacTask.parse()` JDK 25, без анализа типов и загрузки Minecraft. Он содержит 472 объявления типов, 1542 явно объявленных public/protected/неявно public interface методов и конструкторов, 266 полей, imports, generic-параметры, bounds, record components, enum constants, annotations, throws и annotation defaults. Консервативно включены также непубличные типы, кроме private: их открытые члены могут быть унаследованы публичными классами. Это позволяет не ограничивать совместимость пакетом `api`.

Автоматически сгенерированные JVM-методы (record accessors/canonical constructors, enum `values/valueOf`, default constructors, bridges) отдельно не развёрнуты. Их контракт восстанавливается из полных headers и закреплённых исходников. Наследование от Minecraft, binary descriptors, overload resolution и runtime-семантика требуют отдельной проверки на этапе 8. Пробельные символы в отображении сигнатур нормализованы; SHA-256 и Git-источник сохраняют точные annotations, Javadoc и код. Изменение только тела метода может менять семантику, не меняя этого отображения API.

## Архитектурные решения

1. Сохранить `common/`, `fabric/`, `neoforge/`, `buildSrc/`. Один RHI backend в Common; loader lifecycle, registration и hooks остаются в адаптерах. При инвентаризации в Common не найдено imports NeoForge/Fabric. Common включается в loader compilation как исходники и ресурсы; не копировать классы и не создавать дублирующую package metadata.
2. Сохранить все канонические `api/plugin`, `api/registration`, `plugin`, animation graph, managers/controllers, parsers, player/attachment contracts и render plans. Источник этих систем — только MultiLoader. Простое совпадение имён с master не разрешает замену.
3. Новый `content/renderer/rhi/PRhiDrawExecutor` реализует `PRenderExecutor.execute(PRenderPlan, PRenderFrame)`, `capabilities()` и `cleanup()`. `PFrameCompiler` остаётся владельцем группировки/сортировки; backend выполняет готовые команды. Сохранить отдельную `PTransparencyMode` policy, даже когда две группы используют один `RenderType`.
4. `PRhiResourceRegistry` и arena разрешают `PMeshHandle`/`PPipelineHandle` в RHI resources. `PBakedMesh` продолжает хранить `PGeometryData`; GPU allocation/ownership не возвращается в baked model. Сохранить обе ширины indices, динамические updates, close listeners и освобождение handles.
5. UBO layout согласовать с `PInstanceHeader`: transform, ARGB, light, overlay, auxiliary operation/value offsets и count. Donor Std140 layout: mat4 + vec4 + vec2 + vec2 + ivec4, ожидаемый stride 112 байт; проверить фактический layout. При 512 экземплярах payload 57344 байт. Размер блока, размер binding и alignment проверить по device limits. Hardcoded alignment 256 из master не считать универсальным правилом.
6. Делить диапазоны на draws без потери `firstInstance`, `firstIndex`, `baseVertex`, `instanceCount` и порядка. У master все geometry offsets равны нулю, а источник instances — старый `PRenderQueue.InstanceData`; это не подходит современному плану без адаптации. Проверить границы 0/1/511/512/513/1025, несколько групп, отрицательный допустимый `baseVertex`, ненулевые offsets, ushort/uint.
7. Начальная capability selection — реально используемый direct instancing и обычные/RHI mapped uploads. Не заявлять multi-draw indirect/persistent mapping по наличию методов API. `StorageMode` описывает pose/deformer storage, а не UBO instances; не добавлять UBO в enum без необходимости. Сохранить CPU fallback и точное описание feature matrix.
8. Прямые LWJGL/OpenGL, GL object IDs, GL FBO и GL-specific mixins не могут быть обязательным путём общего backend. Публичные `gl/legacy` фасады попали в baseline: сохранять совместимые делегирующие контракты, где возможно. Удаление или изменение GL-типов в signatures требует отдельного объяснения; не оставлять две активные системы исполнения.
9. OIT — четыре полноценных слоя с предыдущим depth input для каждого peel pass. Использовать RHI allocation/pass API донора и современный алгоритм MultiLoader. Композиция учитывает пять vanilla targets и сохраняет непрозрачную глубину. Не копировать двухслойные hardcoded passes или запись destination depth из master как окончательное поведение.
10. Сохранить scope ownership для world/GUI/offscreen/first-person и lifetime deformer streams. GL state snapshots заменить управлением render passes, attachments и scoped host state. Портировать snapshot/restore shared ModelPart и player geometry на новые submit records, сохранив отсутствие утечек между игроками и кадрами.

### Области дальнейшей проверки, без неподтверждённых выводов

- `Identifier`, `Codec`, registry/resource wrappers, Entity/BlockEntity/ItemStack существуют в 26.2; наличие типа не гарантирует совместимость его вызовов. На этапе 2 локализовать реальные compiler errors, сверить с master; не переписывать animation math без причины.
- Сохранить copy identity, независимую identity частичного split и передачу identity при полном split; пустые/неанимированные stacks не должны создавать managers. `ItemStackMixin` сейчас намеренно client-only; проверить dedicated server без переноса client animation классов в common bootstrap.
- Plugin phases: CHANNELS → EVENTS → DEFORMERS → ATTACHMENTS → PLAYER_ANIMATIONS → ANIMATED_ATTACHMENTS → MODELS. MODELS reloadable; остальные однократные. Client-only candidate отфильтровывается до Class.forName. Сохранить изоляцию external failures и fatal internal failures.
- Fabric `AtlasRegistry`, `SpriteSourceRegistry`, ResourceLoader ordering, `LevelRenderEvents`, PIP registration, Armor hooks и plugin filesystem roots требуют проверки опубликованного 26.2 API. Номера новых версий в этапе 0 не выбирались.
- NeoForge `RenderLevelStageEvent`, `RegisterTextureAtlasesEvent`, `RegisterRenderStateModifiersEvent`, `IClientItemExtensions`, camera/armor mixins требуют проверки 26.2.0.57 и Minecraft signatures. Donor не заменяет современные lifecycle hooks.
- AT/AW: проверить QuadrupedModel.body, CubeDeformation.growX/Y/Z, RenderType.create, RenderPipelines registration; `MATRICES_PROJECTION_SNIPPET` не переносить вслепую (donor использует BindGroupLayouts.MATRICES_PROJECTION).

## GPU, shaders, OIT: обязательные проверки переноса

В MultiLoader 12 shader-файлов, в master 10: donor не содержит `oit_fabulous_metadata.fsh` и `oit_fabulous_composite.fsh`. Их алгоритмы сохранить и адаптировать, включая five-target samplers/layouts. MultiLoader передаёт InstanceRow0/1/2, color/light/overlay и ivec4 deformer через attributes 4–10; master читает массив `InstanceDataStruct data[512]` в Std140 UBO через `gl_InstanceID`. Переносить Java layout, shader layout и binding одновременно. Проверить packing ARGB/light/overlay, normal deformation, auxiliary offsets, несколько типов деформеров и CPU/GPU equivalence.

Отдельно проверить минимальный размер binding для объявленного shader block `data[512]`: короткий последний batch не обязательно разрешает binding размером только `count * stride`. Лимит массива в shader, реальный размер allocation/slice и device limits должны согласовываться; если устройство требует меньший batch, Java splitting и shader variant меняются совместно.

Текущий MultiLoader OIT хранит layer depth в color texture с clear 1 и GL MIN blend при сохранённой scene depth; donor использует отдельные D32_FLOAT depth attachments с clear 0, R8_UNORM dummy color, RGBA16_FLOAT accumulation и R16_FLOAT revealage. Сохранить современные alpha/face-color visibility checks: donor peel shader их полностью не повторяет.

MultiLoader normal composite сохраняет opaque/destination depth; donor OIT_COMPOSITE включает запись depth. Сохранить современный контракт и проверить Fabulous insertion между terrain/item entities/particles/weather/clouds. ### Решения по GPU контрактам

- `PDrawCommand.firstInstance` адресует **общий `plan.instances()`**, не локальный список группы. Каждая chunk получает отдельный aligned UBO slice; native draw использует firstInstance=0, поэтому обязательной зависимости от optional nonzero GPU base-instance нет. `firstIndex`, `baseVertex`, порядок групп и экземпляров сохраняются.
- Шейдерный блок выделяется целиком даже для последней неполной chunk; хвост инициализирован нулями. DynamicTransforms — 176 bytes, Projection — 64 bytes; frame matrices поступают из `PRenderFrame`, без изменения RenderSystem globals.
- По умолчанию 128 × 112 = **14336 bytes**, в пределах portable 16 KiB uniform block. Явная capacity 512 требует matching shader и проверенного лимита: 57344 bytes. Native GpuDevice сообщает `minUniformOffsetAlignment`, но не `maxUniformBufferRange`; значение 65536 нельзя объявлять автоматически обнаруженным универсальным пределом.
- На этом GTX 1660 Ti OpenGL query дал block limit 65536/alignment 256; `vulkaninfo` — maxUniformBufferRange 65536/alignment 64. Реальные Vulkan draws прошли и при portable 128, и при проверенной capacity 512. Данные alignment не hardcoded из master.
- `capabilities()` честно возвращает **CPU / DIRECT / WRITE**, matrix NONE. Multi-draw indirect, persistent mapping и shader pose storage не заявляются. Auxiliary fields сохранены; для deformed instances требуются оба extra streams, но сами production GPU deformation shaders ещё не портированы и не проверены.
- В production RHI пакете нет LWJGL/OpenGL/Vulkan backend imports, GL IDs, собственных FBO и GL-specific accessors. Конкретный GpuDevice передаётся снаружи. LWJGL присутствует только в fixture device/window setup и тестовом OpenGL limits query.
- OIT policy не заменена обычной alpha transparency: новый executor **явно отклоняет OIT** до отдельной интеграции четырёх слоёв. Поскольку production executor не переключён, это не отключение существующей функциональности. Включать новый backend для всех passes до завершения этой интеграции нельзя.

### API, ограничения и следующий запуск

**API:** прежние публичные методы, constructors, return types и прямой `PDynamicGeometry` interface в classfiles сохранены. Три класса теперь реализуют новый `PGeometrySource`; `PGlDynamicGeometry`/`PRhiDynamicGeometry` сохраняют AutoCloseable, `GlDynamicGeometry` по-прежнему **не** становится AutoCloseable, что проверено runtime assertion. Новые listeners/accessors — добавления; @Override annotations не меняют JVM signatures. Source declaration headers изменились, поэтому diff не объявляется пустым. Новое поведение failure-path PGl close — техническое исправление lifetime: все RuntimeException callbacks завершаются, затем ошибка распространяется. Полная binary/source compatibility verification остаётся задачей этапа 8; прежние документированные несовместимости этапа 2 актуальны.

**Ограничения:** native RenderType binding не выполняет автоматическую подготовку RenderSetup textures/lightmap/overlay/scissor; caller передаёт matching PRhiMaterial с корректными suppliers. Production material factory/pipelines/shaders и переключение PRenderQueue ещё предстоят. OIT по-прежнему явно отклоняется новым executor, не заменяется alpha blending; существующий production renderer не отключён. Не проверены production game rendering, world/GUI/player, CPU/GPU deformation equivalence, Fabric GPU, четырёхслойный OIT/Fabulous, reload/resize/world unload/device loss, GPU profiling и полная Vulkan compatibility. Прежние offscreen PASS не заменяют эти критерии.

**Следующий запуск:** продолжить **этап 3** — production material/geometry integration и минимальные игровые opaque/cutout/static/dynamic/instancing сценарии.
